## 三、压测中发现并修掉的问题

### 🔴 P0-1 榜单全量排序（性能致命）
- **现象**：原 `submit()` 每次都 `board.sort()` 全榜 + `board.index(e)` 线性找名次 → O(n log n) + O(n)。
- **根因**：并发下每来一个词就重排整张榜，榜单一大必然塌方。
- **修法**：改 `bisect` 增量插入维护降序不变量（`board_keys` 并行列表），**名次 = 插入位置**，彻底消灭全量排序与线性扫描。
- **回归**：`game.py` 自测新增「32 条严格降序 + 重复提交不改变顺序」断言。

### 🔴 P0-2 无界列表内存增长
- **现象**：`guesses` / `history` 是裸 `list`，300 秒一局灌 2 万词就一直涨。
- **修法**：改 `deque(maxlen=2000 / 50)`，`feed` 改 `deque(maxlen=300)`。
- **验证**：压测后 `guesses` 稳定停在 2000 不再增长。

### 🔴 P0-3 `state()` 里 `intels()` 被调 3 次
- **现象**：`intels()` 会跑提示词搜索（`hint_word_in_band` 含 `nearest()` 大矩阵运算），
  每次 `/state` 轮询重跑 3 遍，纯浪费。
- **修法**：单次计算后复用。

### 🟡 P1-1 Flask dev server 性能不足
- **现象**：dev server 下 100 并发 P95 **647ms**、P99 **1252ms**。
- **修法**：新增 **waitress** 生产 WSGI（`--serve waitress`），同样负载 **P95 降到 23ms**（提升约 28 倍）。
- **注意**：waitress 只能单进程多线程。`Game` 是进程内单例，**开多 worker 会让观众词打到不同副本、榜单分裂**。
  真要横向扩展必须先把状态外置（Redis/DB）。

### 🟡 P1-2 `/health` 内存读数恒为 0
- **现象**：`psapi.GetProcessMemoryInfo` 静默返回 0。
- **根因**：ctypes 调 Win32 **未声明 `argtypes`** → `HANDLE` 被按 32 位 int 传递，
  `GetCurrentProcess()` 的 -1 指针被截断 → 调用失败但无异常。
- **修法**：显式声明 `restype`/`argtypes`，读数恢复正常（1103.8 MB）。

### 🟡 P1-3 压测客户端自身缺陷（2 个）
1. **Barrier 死锁**：`poll_mix` 里 `Barrier(users)` 但实际有 `users + users/2` 个线程 → 永远凑不齐 → 全体挂死。
   修为 `Barrier(users + n_poller)`。
2. **中文 URL 未编码**：`/state?viewer=观众` 未百分号编码 → `UnicodeEncodeError`，
   误报「错误率 16.7%」。实为客户端 bug，不是服务端问题。加 `quote()` 后归零。

### 🟡 P1-4 内存统计口径错误
- **现象**：一度报「服务端内存 +778MB」。
- **根因**：用 `tasklist` 汇总**所有** `python.exe`，把压测客户端自己那份 800MB 词表算进去了。
- **修法**：新增 `GET /health` 由服务端自报 RSS（psutil / psapi），压测只读这一个。

## 五、已知上限与后续

1. **单进程单局**：一个进程只能服务一局一个房间。要开多房间必须外置状态。
2. **机器人仍占同步路径**：`bot.py` 每 5 秒调 `submit()`，与观众争同一把锁；
   量小时无影响（1 词/5 秒），但礼物代猜接入后应改成走 `batch_submit` 一次性投递。
3. **提示词搜索是重活**：`hint_word_in_band` 里含 `nearest()` 大矩阵运算（2M × 100），
   目前只在解锁瞬间跑 2 次，已缓存进 `hints` 不再重复。**若要频繁改提示需改用预计算索引。**
4. **`words_seen` 字典随局增长**：一局 2 万词就是 2 万条。实测无压力（+2.6MB），
   但如果要跑一整场直播（几百局），建议在 `_close()` 里清空。
